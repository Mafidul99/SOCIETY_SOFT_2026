# NTCCSL Account Portal

Flutter app for managing the ledger, FD/RD/DRD accounts, Personal Loans, Gold Loans, and users backed by a Google Apps Script web app.

## Configure the data service

**Current loan-sheet routing:** new and pending applications are stored in `Approved_Loans`; approving a loan moves its row to `Loan_Master`, where approved loans and repayment schedules are retained. Rejected applications remain in `Approved_Loans`. `setupAccountPortal` migrates the previous layout, preserving existing records while moving pending/rejected rows to `Approved_Loans` and approved rows to `Loan_Master`. The legacy mirror-routing description in the configuration notes below is superseded by this flow.

Screens are organized as separate Dart files under `lib/pages/`: login, registration, dashboard, ledger, deposit accounts, loans, users, and the signed-in user's profile. The dashboard charts deposit-account counts and estimated maturity by scheme, and shows a permission-aware loan summary with recent applications; its account and metric columns adapt to narrow screens without forcing horizontal scrolling. The existing-collections navigation and its Daily, Weekly, and Monthly pages have been removed. Profile details are available from the account icon in the app bar.

Choose **Appearance** from the navigation drawer to use the device's **System** setting or force **Light** or **Dark** mode. System mode follows the device appearance; page surfaces, forms, dialogs, and headers adapt to the selected theme.

The Apps Script backend is provided in [`Code.gs`](./Code.gs). Attach it to the Google Sheet that will hold the portal data, run `setupAccountPortal` and approve its Sheets and Drive access (setup also creates the private profile-image folder), create the first admin, then deploy the web app as described below.

The bottom navigation provides Dashboard, Loans, FD, RD, DRD, and Users destinations when the account has access; selecting RD or DRD opens its available cadence choices. The navigation drawer contains Loan Master, Personal Loan, Gold Loan, and Approved Loans views. `Approved_Loans` is an automatically synchronized Google Sheets tab containing only currently approved rows from `Loan_Master`. If any loan tab is missing, run `setupAccountPortal` from the bound Apps Script project; it creates missing loan tabs, default Personal/Gold schemes, and the approved-loan mirror while preserving surviving loan records. The approved tab includes the principal, file-charge percentage and amount, processing-fee percentage and amount, and `disbursedAmount` (`principal - fileCharge - processingFee`). Admins configure the two percentage values per scheme in the Loan Master page; both default to 0% until set, and their combined rate cannot exceed 100%. Each loan stores a snapshot of the fee rates and amounts so later scheme edits do not change an existing loan's net disbursement. The Approved Loans page and Personal/Gold pages read the approved mirror; pending and rejected applications remain in `Loan_Master` for review/status tracking. Apps Script refreshes the mirror after create, edit, approve/reject, delete, and direct edits in `Loan_Master`. Setup creates `Loan_Schemes` with separate **Personal Loan Standard** and **Gold Loan Standard** scheme rows when they are missing; each row stores its loan type, minimum and maximum amount (default ₹1–₹1,000,000,000), allowed rate/term range, calculation method, and active status. Admins can add, edit, deactivate, and delete schemes from the Loan Master page; the server blocks deletion when a scheme is referenced by an existing loan. Loan rates are limited to 18–37% annually and terms to 1–7 years. New loans select an active scheme, and Loan_Master stores its `schemeId`, name, and repayment-method snapshot. The backend validates scheme/type/amount/rate/term/method on every create or edit and calculates the persisted figures. Personal and Fixed EMI loans use simple flat-rate interest: `interest = principal × (annualRate / 100) × years`; total repayment is principal plus interest, and the fixed monthly installment is total repayment divided by `years × 12`. Gold schemes also support **Interest EMI**: the borrower pays total flat-rate interest divided by the number of months each month, with the full principal due in the final payment. The scheme form and loan estimate display the selected method and its repayment amounts before saving. Existing `flat` calculation-method values are treated as Fixed EMI. On approval, Apps Script generates and saves a unique random loan number (`LN-year-######`) and the monthly payment schedule, including the final principal balloon for Interest EMI loans. The schedule is stored with the loan, migrated for existing approved records during setup, and shown on approved-loan cards. Admins and Collectors with Loans → Update can mark scheduled payments paid/unpaid; Members and view-only staff can only view the schedule. Editing a loan clears its old schedule until it is approved again. Collectors can add, edit, or delete Loan_Master records and approve/reject loans only when their corresponding Loans role permissions are enabled; Admins always retain access, and only Admins can manage Loan_Schemes. Apps Script enforces role permissions independently of the UI. New loans begin **Pending**; editing a loan returns it to Pending for review. Admins and Collectors with Loans → Update see the approval queue and can approve or reject loans. Collectors granted Edit, Delete, or Update can read the records needed to perform those actions; Collectors with View only receive approved loan records, and Add alone exposes no existing records. Member results are restricted to their own name. `setupAccountPortal` marks pre-existing loans with no approval status as Approved so the migration does not hide existing data. Members also see a **Pay** destination for making a payment. The app-bar account dropdown shows the signed-in user's identity and provides **Profile** and **Logout** actions. The sign-in screen has separate **Admin / Collector** and **Member** choices; the server verifies that credentials belong to the selected role group, and the account's role—not the selected tab—determines permissions. Members can sign in with their registered email address or their account number and password; Admins and Collectors continue to sign in with email and password. Deploy the current `Code.gs` version for account-number sign-in support. Admins can activate/deactivate a Member's Daily, Weekly, and Monthly deposit-report cadence access from Users → Edit; Apps Script enforces these switches on every deposit read. **View deposit accounts** and **Manage deposit accounts** are independent role permissions configured by Admins. Management includes creating/editing/deleting accounts and tracking installment payments; it also grants the read access needed to manage them. Member viewing is configurable, but Members are always read-only and Apps Script blocks all deposit writes. The navigation drawer groups FD, RD, and DRD accounts under Deposit → New FD/RD/DRD: FD is monthly, RD is weekly or monthly, and DRD is daily, weekly, or monthly. FD stores one principal and estimates maturity using monthly compounding: `principal × (1 + r / 12)^tenureMonths`, where `r = annualRate / 100`. RD and non-daily DRD accounts estimate maturity with cadence-matched installment compounding: `installment × (((1 + i)^installmentCount - 1) / i)`, where `i = r / periodsPerYear` (`365` daily, `52` weekly, `12` monthly); at zero interest, maturity is installment × count. **Daily DRD** instead estimates simple interest on total scheduled contributions: `installment × installmentCount × (1 + r × tenureMonths / 12)`. For example, a 300 daily installment, 7% annual rate, 365 installments, and 12-month tenure gives 109,500 in scheduled contributions and a 117,165 maturity estimate. The account's received amount remains based on installments actually marked paid. The configured annual interest rate and tenure are captured per account; tenure is limited to 1–120 months and rates to 0–100%. These are estimates and do not include tax, penalties, missed-payment adjustments, early closure, or payout rules. Admins can use the Users page role tabs to view and add Admin, Collector, and Member accounts, and the **Roles & Permissions** navigation page to configure role-level access. Users → Add/Edit lets authorized account managers upload a JPEG, PNG, or WebP profile image (maximum 300 KB); images are kept in a private Drive folder and are returned only through authenticated portal responses. The Users directory and signed-in profile show the image, with initials as a fallback. Admins always retain full access; only Admins can assign roles or edit role settings. App startup displays the centered Flutter splash page; the native Android and iOS launch screens stay plain white so the previous logo splash does not appear before it.

Loan sheet headers now match the requested contract: Loan_Master follows `id, loanNumber, schemeId, schemeName, memberName, loanType, startDate, principal, annualRate, tenureYears, totalInterest, totalPayable, monthlyInstallment, repaymentMethod, paymentSchedule, approvalStatus, reviewedAt, reviewedBy, fileChargePercent, processingFeePercent, fileCharge, processingFee, disbursedAmount, createdAt, createdBy`; `loanNumber` remains blank until approval and `paymentSchedule` stores the generated monthly dates, amounts, and payment statuses as JSON. Loan_Schemes follows `schemeId, schemeName, minAmount, maxAmount, loanType, minAnnualRate, maxAnnualRate, minTenureYears, maxTenureYears, calculationMethod, active, fileChargePercent, processingFeePercent`. Approved_Loans uses the Loan_Master columns. Personal/Gold pages display approved applications only and retain role-authorized application and review actions.

Pending and rejected applications remain in `Loan_Master`; approved records are mirrored to `Approved_Loans`, which is the source for the Approved Loans page and approved entries on the Personal and Gold Loan pages. Members see only their own applications.

On **Roles & Permissions**, Admins open a module dropdown and toggle individual View, Add, Edit, Delete, and Update actions for Collector and Member roles. Each switch saves immediately; if saving fails, the switch is restored and an error is shown. The Role_Permissions sheet is extended from its legacy role-wide flags and setup migrates existing access to the corresponding action flags. Update means ledger amount/balance edits, deposit payment status changes, loan approval/rejection, or Admin-only user role/access changes. Collectors can be granted loan Add, Edit, Delete, and Update actions independently; loan Add creates a Pending record, Edit returns a record to Pending, and Update allows review of Pending loans. Edit/Delete/Update grants also expose the records needed for those actions, including the approval queue for Update; Add remains available without exposing existing records. Admin-only user role/access changes, role settings, and loan schemes remain restricted to Admins. Members can toggle loan viewing and loan applications separately and cannot edit, delete, or approve loan records.

The Loans drawer is role-specific. Admins see all four destinations: **Loan Master** (scheme overview and pending approvals), **Personal Loan**, **Gold Loan**, and **Approved Loans**; Admins have all loan permissions enabled. Collectors see **Personal Loan** and **Gold Loan**, plus **Approved Loans** when they have loan View or a loan record-management permission. Members with loan application or View access see **Personal Loan**, **Gold Loan**, and **Approved Loans**; the backend restricts Member results to their own applications. Each loan page reloads its records when selected, so approvals made elsewhere become visible on the matching Personal Loan or Gold Loan page and in Approved Loans. The four destinations are implemented as separate widgets in `lib/pages/loan/`; the shared loan form and record UI lives in `loan_page_content.dart`.

### Member loan applications

Members can open Personal Loan or Gold Loan from the navigation drawer and submit an application without loan-view permissions. The server takes the applicant name from the authenticated Member account (it does not trust a submitted name), creates the loan as **Pending**, and lets the Member view their own application status. Members cannot edit or delete applications, manage schemes, or approve loans; those actions remain Admin-only. Collectors cannot apply for loans. Loan pages are in the navigation drawer; the bottom navigation contains Dashboard, FD, RD, DRD, and Users, with Pay also shown to Members.

## Role access

Admins always have full access. Admins configure Collector permissions and Member read access from **Roles & Permissions**. Members can be allowed to read shared data and deposit accounts. For ledger, deposit, loan, and user records, Edit/Delete/Update access includes visibility of the records needed to perform the granted action; Add alone does not reveal existing records. Member results remain restricted to their own deposit and loan records, and Member deposit-report cadence access is enforced. Member deposit-management, ledger-management, and user-management permissions are always false, cannot be enabled in the page, and are forced off by the backend even if a direct API request attempts to enable them. Admins separately activate or deactivate Daily, Weekly, and Monthly deposit-report cadence access for each Member account from the Users editor. Inactive cadence reports are hidden after that Member signs in again and are also blocked by Apps Script. Role-level settings are stored in the Google Sheet's `Role_Permissions` tab; individual cadence switches are stored on the corresponding `Users` row. Only Admins can assign roles, change role settings, or manage Member cadence access.

Ledger entry attribution is selected from `1 mafidul`, `2 mohibul`, and `3 Asrsful`.

Each user has a role-specific `accountNo` displayed on the profile and Users directory: Members receive sequential IDs starting with `DRD000000001`, Collectors receive sequential IDs starting with `EMP000000001`, and Admins receive a unique random nine-digit ID prefixed with `ADM`. Internal UUIDs remain unchanged for authentication and user management. Run `setupAccountPortal` after updating the script to add the account number column and migrate existing users to the role-specific format. New users receive an account number automatically.

The profile page displays the account's profile image, email, and phone number. Signed-in users can update their optional 10-digit phone number from **My profile → Edit profile**; Admins can also add or edit phone numbers in **Users → Add/Edit**, and phone numbers are searchable in the Users directory. The phone number is carried into the Cashfree payment form. Account managers can upload or remove a profile image from **Users → Add/Edit**. Images are stored privately in Google Drive; only users authorized to view the account directory (and the account owner at login) receive image data. The login page's **Forgot password?** option directs users to contact an administrator, who can reset a password from **Users → Edit → New password**. Passwords are stored as salted hashes and cannot be retrieved or displayed; the eye button only reveals text while entering a new password.

## Cashfree payments

Members can pay for their own account from **Make a payment**. Admins and Collectors with shared-data-read or user-management permission can search active Members by name, email, or phone and initiate a payment for the selected member. Account numbers are not shown, required, or used in Cashfree checkout; the internal member ID is used as Cashfree's customer ID. Customer name and email are editable and optional; a valid 10-digit mobile number is required. RD/DRD deposit and approved Gold/Personal Loan schedules have a **Pay next** button targeting that schedule's next unpaid installment. Schedule checkout locks the installment amount, adds the 2% service charge, and sends the exact schedule item to the backend; the server revalidates the member, amount, loan approval, installment index, and unpaid status. The general **Make a payment** form requires an amount matching an unpaid deposit installment. After Cashfree reports success, Apps Script verifies the order and marks the selected deposit or loan schedule installment paid; general payments apply to the oldest matching unpaid deposit installment. The result is recorded in `Payment_Transactions`. Flutter opens a payment confirmation page only after the server confirms payment, displaying whether the schedule was updated. If no matching installment remains when the payment is verified, the confirmation page warns that the schedule needs administrator reconciliation. Schedule updates are idempotent when the payment is verified again. Cashfree secrets are never sent to Flutter.

Before enabling checkout, set `CASHFREE_APP_ID` and `CASHFREE_SECRET_KEY` to your production credentials in the bound Apps Script project's **Project Settings → Script Properties**. `CASHFREE_ENVIRONMENT` defaults to `production`; set it to `sandbox` only when testing with the matching sandbox App ID and Secret Key. A 401 order-creation response means the credentials and environment do not match or Cashfree has rejected those credentials. Other Cashfree order rejections return the provider's bounded error code/message to help identify invalid order details. Never put credential values in `Code.gs`, Flutter, source control, or chat. After backend changes, save the updated `Code.gs` and deploy a new web-app version so schedule updates are enabled for the app. Flutter uses Cashfree's official SDK, while the backend remains the authority for the order amount and payment status.

## Install and run the Apps Script backend

For an already configured workbook, save the updated `Code.gs`, then run `migrateDepositPaymentRows` from the Apps Script function dropdown or use **NTCCSL Portal → Update deposit payment columns**. The migration creates one native Boolean column per installment (`P1`, `P2`, through `P365` for a 365-period schedule; longer schedules continue as `P366` and higher), adds numeric `payment_count` and `paid_count` columns, and removes old `payment_N_paid` columns, the JSON `payments` column, any `paymentRows` column, and the legacy `Deposit_Payments` tab. The app still receives its `payments` list, generated from the `P#` columns. `payment_count` is the number of scheduled installments; `paid_count` is the number marked `TRUE`. Counts are refreshed when the app updates payments or when an installment Boolean cell is edited directly in the sheet. The full `setupAccountPortal` routine also performs this migration.

1. To keep the supplied account data, use your existing `NTCCSL_ACCOUNT (2).xlsx` workbook. To start with empty sheets, use the [NTCCSL_Account_Portal_Template.xlsx](./NTCCSL_Account_Portal_Template.xlsx) workbook instead.
2. Upload the chosen workbook to Google Drive and open it with Google Sheets. Use **File → Save as Google Sheets** to convert it into a native Google Sheet. An `.xlsx` file cannot host the live Apps Script deployment.
3. Open the converted Google Sheet, then select **Extensions → Apps Script**. This step is important: it creates/opens a script bound to this specific spreadsheet. Do not create a separate project at `script.google.com` for this setup.
4. In that bound Apps Script project, replace the editor contents with [`Code.gs`](./Code.gs) and save.
5. In the Apps Script editor, select `setupAccountPortal` in the function dropdown and click **Run**. Review and approve the requested Google permissions. Wait for the execution to finish successfully. This stores the spreadsheet ID and password secret in this Apps Script project's Script Properties and creates any missing tabs/headers, including `Role_Permissions`, `Payment_Transactions`, and `Bank_ladger`, and `phoneNumber` and Member cadence-access columns on `Users`. An existing `Amount` tab is renamed to `Bank_ladger` while preserving its data. If both `Amount` and `Bank_ladger` already contain data, setup stops so you can merge the ledger rows without risking data loss, then rerun setup. `Loan_Master` gains approval status and reviewer columns; existing loans without a status are marked Approved. `Deposit_Accounts` has one native Boolean column per scheduled installment (`P1`, `P2`, through `P365` for 365 installments; longer schedules continue as needed), numeric `payment_count` and `paid_count` summaries, and no JSON `payments` column; the app derives its Boolean `payments` list from `P#` columns. `payment_count` is the number of scheduled installments; `paid_count` is the number marked `TRUE`. Installment dates and amounts are computed from the account terms; no `paymentRows` column or separate `Deposit_Payments` tab is required. Setup migrates paid/unpaid state from an older JSON `payments` column, older `payment_N_paid` columns, a `Deposit_Payments` tab, or a `paymentRows` column into the `P#` Boolean columns, then removes those old stores. Existing users with blank cadence-access cells retain access by default. Existing role settings are preserved except that Member write permissions and role-restricted Admin actions remain disabled for Members. Deposit view/manage permissions are initialized, using legacy permission values where present; Admins can adjust them independently in **Roles & Permissions**. If no saved settings exist, Collector loan Add, Edit, Delete, and Update permissions default off and can be enabled individually by an Admin; Member defaults to deposit read-only and may be granted loan viewing/application access. `setupAccountPortal` permanently deletes the three old collection tabs and their data; export or back up the workbook first if those records need to be retained. The old collection records are not migrated or archived.
6. Return to the Google Sheet and reload it. Confirm these tabs exist: `Users`, `Bank_ladger`, `Deposit_Accounts`, `Approved_Loans`, and `Payment_Transactions`, and that `Deposit_Accounts` has `payment_count`, `paid_count`, `P1`, `P2`, through the required `P#` columns, but no `payments`, `paymentRows`, or old `payment_N_paid` columns. The old collection tabs and any migrated `Deposit_Payments` tab should be gone. To enable Cashfree, configure the credentials in Apps Script Script Properties as described above. The imported workbook already has user records, so use **NTCCSL Portal → Reset admin password** to set a new password for an existing active administrator. Password hashes in an `.xlsx` export cannot be used without the original Apps Script project's secret. If the Users tab is empty, use **NTCCSL Portal → Create first admin** instead. Do not share the sheet or Apps Script editor with ordinary app users.
7. To install the AdminLTE web panel, create an **HTML** file named `Admin` in this same Apps Script project and paste in [`Admin.html`](../ntccsl_admin_web/Admin.html). Keep it in the same project as `Code.gs` and the target spreadsheet. The panel is served at the deployment URL with `?panel=1` (for example, `/exec?panel=1`) and supports Admin, Collector, and Member sign-in. Choose **Admin / Collector** for staff email sign-in; Members can sign in with their email or account number. The panel shows pages based on the signed-in role permissions, and Apps Script enforces permissions for every action. It calls the same Apps Script actions and spreadsheet as the Flutter app; edits made by either client are shared. Use the theme control on the sign-in screen or in the top bar to cycle between **System**, **Light**, and **Dark**; the selection is saved in that browser, and System follows the device appearance. AdminLTE, Bootstrap, jQuery, and Font Awesome load from public CDNs, so the panel requires an internet connection.
8. In the **same bound Apps Script project**, choose **Deploy → New deployment → Web app**. Set **Execute as** to your account and **Who has access** to the intended app audience. The app calls the web app as a public endpoint, so access may need to be “Anyone”; in that case, every action is protected by its server-side session-token and role checks. Do not use this deployment with sensitive financial records until you have reviewed the security limitations below.
9. Copy the deployed `/exec` URL and use it in Flutter:

   ```sh
   flutter run --dart-define=GOOGLE_SCRIPT_URL=https://script.google.com/macros/s/DEPLOYMENT_ID/exec
   ```

10. After changing `Code.gs` or `Admin.html`, create a new deployment version or update the existing deployment. Saving the editor alone does not update an already deployed version. The first role-permissions request creates the `Role_Permissions` tab and initializes it if it is missing; alternatively, run `setupAccountPortal` in the bound project. Confirm the tab contains one row for `Collector` and one for `Member`.
11. Sign in with the administrator whose password you set in step 6 to manage accounts and permissions. Collectors can use the panel features enabled by their configured permissions. Members can sign in with their email or account number and see only records the backend allows for their account; Members cannot change protected records. Public self-registration creates a `Member`, not an admin.

### Fix: “Spreadsheet is not configured”

This means the deployed script project has no `SPREADSHEET_ID` in its Script Properties. Run `setupAccountPortal` from the **Apps Script project opened through the target Google Sheet** (steps 3–5 above). Running setup in another or standalone Apps Script project will not configure the deployed web app: Script Properties belong to one script project and are not shared between projects.

After setup succeeds, confirm the web app deployment was created from that same bound project. If you accidentally deployed another Apps Script project, deploy this bound project and replace Flutter's `GOOGLE_SCRIPT_URL` with its `/exec` URL. The Flutter request itself cannot initialize the spreadsheet; setup is a one-time owner action.

The `Bank_ladger` tab uses the headers created by setup and stores ledger entries. Run `setupAccountPortal` to rename the old `Amount` tab and remove the old collection tabs; the collection-tab deletion is permanent, so back up the workbook first if you need those records.

## Security and verification notes

Passwords are never stored in plaintext. This Apps Script implementation uses a per-user salt and an HMAC-SHA-256 digest keyed by a random secret stored in Script Properties, along with expiring server-side session tokens and role checks on every protected action. This is a lightweight Google Apps Script implementation, **not a 100% security guarantee or a substitute for a dedicated identity provider**. Apps Script does not provide a built-in memory-hard password hashing API; for sensitive production financial data, use Firebase Authentication or another established identity provider and a backend designed for that security requirement. Limit Apps Script editor access, keep the spreadsheet private, and protect a web app accessible to “Anyone” with strong credentials and monitoring.

The last active administrator cannot be demoted or deleted. Script-side errors are returned as `{ "status": "error", "message": "..." }`; the Flutter UI must not be treated as an authorization boundary. Never type passwords or password hashes into the Users sheet; account creation and password hashing happen through Apps Script actions.

Local tests verify Flutter UI behavior and the client/server JSON contract with simulated responses. They cannot verify deployment permissions, Google Sheets contents, Apps Script quotas, or real credentials. Complete the live sign-in, registration, role-denial, and CRUD smoke tests after deploying to your own spreadsheet.

The login session is kept in memory and is discarded when the user signs out or closes the app. Configure `GOOGLE_SCRIPT_URL` to point to a deployment of the current `Code.gs`; an older deployment may not support the current login and registration actions. Local widget tests verify the UI and expected API contract; they do not prove that the deployed Apps Script or production credentials work.

The app has a default endpoint in `lib/main.dart`. To use another deployment URL, pass it at run/build time:

```sh
flutter run --dart-define=GOOGLE_SCRIPT_URL=https://script.google.com/macros/s/DEPLOYMENT_ID/exec
```

If the endpoint returns HTML, an error page, or a response with an unexpected JSON shape, the affected screen displays the service error and a retry button rather than showing a misleading empty list.
